## Try it in Unity

In Unity's **Project** window, open `Assets/DEV505/SoundManager/Samples/09-Portals/Demo.unity`. The supplied scene already has its Sound Manager, event registrations, generated keys, camera, and Audio Listener. Press **Play**, wait for the demo to be ready, and click the **Game** view before using the keyboard. If you are setting up a separate scene, follow <a href={sitePath('getting-started/')}>Your first sound</a> first.

| Control                       | Action                                                      |
| ----------------------------- | ----------------------------------------------------------- |
| **Space** / Step through      | Cross to the other world, or wake the portals when closed.  |
| **E** / Echo lingers          | Toggle the departure's owner-loss policy between crossings. |
| **X** / close-or-wake control | Close or wake the portals.                                  |

Begin in Mint Meadow with Echo lingers enabled. Step through, and listen behind you as the departure echo continues while the destination ambience arrives. Turn Echo lingers off and cross again. This time the same departure recording stops when the outgoing sound object is removed.

The player and listener travel together. The change you hear comes from both source placement and listener movement. These are two destinations **inside one Unity scene**; the demo does not load or unload scene files.

## Five events, one clear ownership story

| Event                  | Role                                                      |
| ---------------------- | --------------------------------------------------------- |
| `Sounds.PortalWorld`   | Loop the selected world's ambience.                       |
| `Sounds.PortalHum`     | Loop the portal's nearby hum.                             |
| `Sounds.PortalEcho`    | Departure recording with owner loss set to Detach.        |
| `Sounds.PortalCut`     | The same departure recording with owner loss set to Stop. |
| `Sounds.PortalArrival` | Short cue on arrival.                                     |

The controller creates a temporary audio-rig GameObject at the gate and obtains `service.OwnerOf(rig)`. World and Hum follow that object's Transform and share its owner. `PortalWorld.Ambience` initially selects Meadow or Crystals from its allowed clip list.

<Capture id="portals-graph-portalworld" />
<Capture id="portals-graph-portalhum" />

The ambience and hum graphs start loops and respond to stopping. During departure, Echo or Cut starts on the outgoing rig. Midway through travel, the controller destroys that rig. Its owner and follow target are now gone.

<Capture id="portals-detach-settings" />
<Capture id="portals-stop-settings" />

Owner-loss Stop retires the world ambience and hum. With Echo lingers enabled, the departure uses **Detach**: the runtime drops the missing target and lets playback finish at the last known position. It does not attach the old echo to the arriving player. With Echo lingers disabled, PortalCut uses **Stop**, so that departure ends with its owner.

<Capture id="portals-graph-portalecho" />
<Capture id="portals-graph-portalarrival" />

The destination creates its own audio rig, starts its ambience and hum, and adds Arrival. The old echo and new world can therefore overlap without belonging to the same lifetime.

## Follow and own are separate choices

```csharp title="Start on a temporary rig · excerpt"
var owner = service.OwnerOf(rig);
var context = SoundPlayContext.Following(rig.transform, owner);
var result = SoundBus.Play(Sounds.PortalEcho, context);
```

`rig` is a GameObject and `service` is ready. Following supplies the position; the owner token groups the interaction's lifetime. Destroying the rig later lets each event apply its authored owner-loss policy.

Do **not** call StopOwned as part of the Detach comparison. That explicitly asks all owned plays to stop, removing the behavior you are trying to hear. Owner loss and an explicit stop request are different operations.

The full controller keeps its handles, including detached departures. On disable it explicitly stops those handles and destroys remaining rigs, so leaving the demo does not leave echoes behind. The smaller recipe demonstrates the two policies using one temporary object and a short delay before destruction.

## What belongs to the demo?

The crossing animation, islands, world selection, listener travel, portal glow, and rig creation/destruction belong to `PortalsDemo`. Sound Manager supplies ownership, following, event-specific loss policies, and sound playback. Detach preserves sound position and lifetime; it does not preserve the destroyed visual object.

## Common surprises

- **The echo vanishes even with Detach.** Check for an explicit StopOwned or StopAll call before destroying the owner.
- **The echo moves with the destination.** Keep the outgoing sound on its own rig; do not reuse the player as its follow target.
- **The echo survives after leaving the demo.** Retain detached handles and stop them during controller cleanup.
- **A scene-loading system is expected.** This sample uses GameObject destruction within one visible scene. Adapt ownership to your own scene-loading lifecycle separately.
